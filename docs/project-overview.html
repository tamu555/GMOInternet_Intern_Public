疑似レジストラサービス 計画概要

事前知識ゼロでも、ドメイン取得からDNS設定・維持までひとりで完走できるレジストラ。

更新 2026-08-25 期間 5日間ハッカソン

TARGET

ターゲット：ドメイン未経験の個人・初学者

UX原則は「小学生でも使える」。判断基準に迷ったら、常にこのペルソナが完走できるかで決める。

ペルソナ
佐藤 悠（19歳・大学1年生）。HTML/CSSやReactは少し触った。ドメイン・DNSは未経験
きっかけ
就活・サークル・個人開発のサイトを独自ドメインで公開したい（yuu-portfolio.com）
つまずき
どこで買うか分からない。.comと.netの違いも曖昧。購入後に「ネームサーバー」「CNAME」が突然出てくる
求めるもの
「何をしたいか」を選ぶだけで必要な設定まで案内され、「サイトが公開されました ✓」まで到達できること

PURPOSE

目的：知識ハードルを外し、「安心して維持できる」まで面倒を見る

既存サービスは事前知識を要求し、サイト内導線も分かりにくく、初学者には参入ハードルが高い。本サービスは専門知識を極力排したUIで取得 → DNS設定 → 維持を一気通貫で支援する。ただし専門用語を消し去るのではなく併記し（例：「ネームサーバー（どのDNSに任せるかの指定）」）、学習して通常モードへ「卒業」できる導線を作る。

通常モード知識がある人向け

ドメイン一覧・検索を起点に全項目を表示・操作。コア機能はすべてここに実装する。

簡単モード事前知識ゼロ向け

「何をしたいか」を起点に、必要な項目だけをフローチャート＋進捗つきで案内。通常モードのAPIを呼ぶ薄いウィザードとして実装する。

理由：5日間でUIを二重実装すると破綻する。ドメイン操作ロジックは1本に保ち、通常モードを先に完成させてから簡単モードを載せる。

FEATURES

主要機能と選定理由

機能 区分 内容と選定理由
コア6機能 必須 登録・更新・情報修正・廃止・復旧・移管（IN/OUT）＋情報参照。レジストラとしての土台。EPP相当APIで正しく動くことを最優先で保証する。
ユーザー関連 必須 ユーザー登録/削除、ユーザー認証、ログイン/ログアウト。ユーザー周りの機能を担う。
2レジストリ対応 必須 Kitaqsign / Kitaqnic の差分（pollのack方式がパスもHTTPメソッドも違う等）をBRIDGE層に閉じ込める。レジストリごとの差分を上位層に漏らさず、レジストリ追加にも耐える構成にするため。
目的起点ウィザード 差別化 「Web公開／デプロイ／メール」の目的選択から、候補提案 → 決済 → DNS設定 → 維持まで進捗表示つきで案内。進捗の完了条件はボタン押下ではなく実データで判定（再ログインしても正しい位置に復帰）。「安心」の実体は正確な進捗復帰。
AI入口（協議中） 検討 「やりたいこと」の自由文入力をAIが解釈し目的分類へ変換。おすすめTLDのデフォルト提示で「とりあえずこれなら良さそう」に導く。AIの役割は生成でなく解釈→分類に限定。IntentParserで抽象化し、ルールベース／Claude API／ブラウザ内モデルを差し替え可能に。TLD推薦自体はルールベースが担当。
レンタルDNS（自作） 必須 A/CNAME/MX/TXTを保持し、自前リゾルバAPIで「確認する」ボタンに応答。レジストリはNSまでしか持たないため、DNS設定機能を持つなら自作が必須。「レジストリはNSまで、レコードはレジストラの責務」という業界の切り分けの再現でもある。
DNSレシピ＋貼り付けパーサ 差別化 Vercel等の主要サービス別テンプレを選ぶだけで一括投入。設定案内のコピペをパースしてレコード案に変換。初心者最大の壁「そこに何を書くか」を選択肢化する。テンプレ追加＝JSON追加のみで仕様変更耐性の実例にもなる。
エラー回復UI 差別化 決済成功→create失敗などの中途半端な状態を自動リカバリし、「処理中です。自動で再試行しています」と正直に見せる。通信エラー時の振る舞いはデモの見せ場。二重課金を防ぐ冪等リカバリ（2302＋info成功＝前回成功と解釈）が本体。
維持ダッシュボード 必須 残り期間・自動更新の状態・支払い方法の状態を同格で表示。状態別の色分け一覧。擬似レジストリは自動更新されるため「失効の恐怖」は演出できない。実際にドメインを失う原因（支払い方法の期限切れ）を可視化する方が誠実。

ARCHITECTURE

構成：レイヤ分割

[ Web UI ] 通常/簡単モード（UIは1セット） │ [ API層 ] 会員・注文・進捗・価格・DNSレコード ├── [ 自作 権威DNS ] A/CNAME/MX/TXT ├── [ BATCH層 ] Pollワーカー×2・期限監視 └── [ BRIDGE層 ] レジストリ差分の吸収 ├── KitaqsignClient └── KitaqnicClient

TLD→レジストリのルーティングは起動時にsessions/helloのsupportedTldsから自動生成し、ハードコードしない。

DECISIONS

主要な設計判断

ゴミ箱UIは採用しない → 状態別の色分け一覧決定

ゴミ箱は「無料でいつでも戻せる」という期待を作るが、ドメインの実態（猶予期間・復旧料）と食い違う。ライフサイクル終盤の複数状態を1つの場所にまとめるのも無理がある。アクティブと終盤をセクション分けし、状態ごとに色＋ラベルで表示する。

候補提案のコアはルールベース、AIは限定適用協議中

AIを使うなら価値が出る2点（自由文の解釈、日本語→ドメイン文字列変換）に限定し、デモはルールベースのフォールバックで確実に動かす。API費用はこの使い方なら1回約0.3円。

実測ファースト：コードを書く前にDay1でAPIを叩き切る決定

仕様書に載っていない挙動（復旧の猶予期間、移管後のexDate、pollの空応答など）は8本の実測テストで確定させてから設計を固定する。飛ばすとDay3〜4に設計やり直しが発生する。

レジストラを2つ発行し、移管を自前で完結決定

APIキーは自己発行できるため、A=サービス本体、B=「他社レジストラ」役を用意。移管IN/OUTの検証・デモが自前で完結し、移管OUTの承認画面も自然に必須機能になる。

モック時計で時間をデモ可能にする決定

猶予期間は日単位でデモの5分では見せられない。表示用の基準時刻を差し込める設計を初期から入れる（後付け不可）。早送りは表示演出であり、実態とズレないようデモ用データを仕込む。
